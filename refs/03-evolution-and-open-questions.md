## 不要沿用的历史误读

| 可能的误读 | 需要恢复的上下文 |
| --- | --- |
| Daythread 就是任务管理工具 | 资料被重新利用、个人记录和 dashboard 是起点的一部分；首轮可以做取舍，但要说明尚未验证的价值 |
| 用户不需要提醒或 e-ink | 用户明确提到它们；延后是降低第一轮成本的建议，不是长期需求撤回 |
| 首版 AI 简单，所以可以只做手工任务列表 | 用户选择保留自然语言模型处理；简化的是检索、prompt 和上下文工程 |
| Pages／Blocks 细节都已由用户逐项指定 | 用户明确要求存放与引用；段落级引用、反向引用、数据模型等是具体设计，来源不同 |
| 文档里用了“已确认／正式规格”，就无需审核 | 最新用户消息明确产品与技术未定稿 |
| 五个角色是严格的文件／能力边界 | 用户要求通用方案；角色是主要责任，可以跨职责协作 |
| 同意一轮评审等于同意所有后续实验、预算和时间安排 | 评审产生的是建议，接受范围与外部操作仍要依据实际授权 |

## 与当前团队评审核对的重点

本次看到的 `docs/reviews/round-1/synthesis.md` 已引用探索记录，提出 R1–R11，且 `docs/specs-v0.2/` 已形成修订草案。因此应做增量上下文核对，而不是认定团队此前完全没有背景。

| 当前建议或讨论点 | 需要回到的原始上下文 | 应怎样处理 |
| --- | --- | --- |
| 结构化 Today 区与自由正文两种布局 | O-U06 希望行动安排包含在可修改的自由书写页 | 说明怎样支持真实写作，记录两种方案取舍，不能靠团队偏好当作用户选择 |
| 引入基线、原型、人工 concierge，延后正式代码 | O-U08–O-U10 希望少假设、低成本验证功能／loop | 比较总时间、用户投入、验证能力与最小可用版本；方法本身是待选建议 |
| 仅显示前三条接续，或增加 open pool | O-U07 担心库存与维护负担 | 同时验证找回可靠性与日常负担，不能只用“能查到”证明问题已解决 |
| 资料主动回流 | O-U03 的问题正是收藏后不再访问 | 手动引用可验证基础能力，但不能单独证明系统解决了重新利用问题；自动化程度仍需取舍 |
| 模型上下文截取、摘要或预算限制 | O-U10 希望先直接给输入与已有信息，避免前置优化 | 必要限制应有实际容量／成本依据，并解释对验证的影响，不默认为用户改了偏好 |
| Block 级引用是否必须、是否可以缩减 | O-U11 的真实措辞，而不是后来 U07 编号的概括 | 先纠正来源归属，再按目标比较方案；本 refs 不替用户批准删除或保留具体形式 |
| 开始日期、截止、暂放、AI 修改确认等规则 | 用户目标、助手推演和当前团队建议混合 | 逐项区分来源，检验一致性与操作成本，避免只因规则更完整就视为更好 |

本次只标出应核对的出处和差异，没有判断某条评审一定错误，也没有改动团队现有报告。

## 还缺什么上下文

- 一份真实 daily note 的结构与书写方式：能判断是否需要事项与自由文本交错。
- 当前 review 的实际习惯：哪些是已有行为，哪些需要系统帮助建立。
- 每日捕获、规划和回顾用什么设备。
- 什么资料曾有机会帮助行动，却没有被找回来：用于设计与验证资料复用。
- 各验证方法愿意投入多少用户时间，以及真实模型调用的范围与预算。

这是一份已知缺口清单，不要求团队马上向用户批量追问。先使用已整理的来源和可以自行判断的内容，再由 Lead 集中提出真正影响下一步的问题。

## 后续维护

用户的新决定应记录日期、原话或消息出处，并同步当前简报／方案。新的来源可以追加到 refs，并注明它改变了什么。历史复制件保持原样；摘要可以修订，但不能无声改写原话。

当前团队配置快照在 [team/](team/raft-agent-team.md)，Daythread 本轮目标在 [评审简报](team/daythread-agent-team.md)。下一轮应结合此 refs、现有评审和最新用户反馈，明确继续采用的方案版本。
