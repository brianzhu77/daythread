# 产品背景与需求来源

这是带来源的整理，不是新增产品要求。原话索引 O 来自 2026-10-13 至 10-14 的探索；C 来自 2026-10-15 的团队规划。所有链接指向本目录中的可追溯消息。

## 为什么想做这个产品

用户从 Karpathy LLM Wiki 的讨论出发，希望自己做一个更个人化的 App，把知识整理、daily note 和 dashboard 联系起来。[O-U01](02-user-quotes.md#o-u01)、[O-U02](02-user-quotes.md#o-u02)

最初明确表达的痛点是：

| 原始处境 | 用户想获得的改变 | 来源 |
| --- | --- | --- |
| 每天在 Notion 写 daily note，未完成事项需要接续；规划和 recall 消耗精力 | 提醒每日 review、引导 routine、预先生成次日计划 | [O-U03](02-user-quotes.md#o-u03) |
| 把文章、视频和 GitHub 项目收藏到 Notion，之后基本不再访问 | 让已有零碎内容真正产生价值，而不只增加存量 | [O-U03](02-user-quotes.md#o-u03) |
| 已有 TRMNL e-ink 屏幕，期望作为 dashboard 出口 | 看见当下重要的 Top 3、TODO、quotes／notes；具体屏幕系统并不重要 | [O-U03](02-user-quotes.md#o-u03) |
| 在当日日记写了未来事项，之后需要回忆或翻找 | 对应日期或临近日期在 daily note 体现；Calendar 是当时提出的候选出口 | [O-U04](02-user-quotes.md#o-u04) |

用户自己的概括是：“其实有点像用 daily note 串起来所有的事。”它表达组织意图，不单独决定数据库结构或界面布局。[O-U04](02-user-quotes.md#o-u04)

## 体验上的重要表达

1. **自然语言 Home。** 作为每日入口，输入可以包含 TODO、Events、Notes、链接和带日期事项。自动抓取与 wiki 是最初想法，后续允许首版手动收集。[O-U05](02-user-quotes.md#o-u05)、[O-U11](02-user-quotes.md#o-u11)
2. **Suggested 自由书写页。** 用户提出“包含了今天的行动安排”“页面的内容可以完全被修改”。这值得用真实写作流程检验，不应只解释为可编辑任务标题。[O-U06](02-user-quotes.md#o-u06)
3. **减少维护负担。** 用户担心“移出今天”导致总待办巨长、无法维护，也不希望每次移除都选择去向。具体暂放规则、候选上限和找回频率仍来自后续设计。[O-U07](02-user-quotes.md#o-u07)
4. **少假设、低成本验证。** 用户希望框架清楚后通过低成本 MVP 测功能／loop 是否顺畅。这是评估研究、原型、人工验证和直接实现成本的背景，不能自动推导成任何一种验证方法已获选择。[O-U08](02-user-quotes.md#o-u08)、[O-U09](02-user-quotes.md#o-u09)

## 首版取舍是怎样形成的

- 用户接受独立 Web app，不希望首版做 Notion 数据迁移，接受人肉同步信息。[O-U09](02-user-quotes.md#o-u09)
- 用户选择保留自然语言和真实 AI，直接把输入与已有信息交给模型，暂不优化提示词、检索或上下文。简化 AI 不等于首版去掉 AI。[O-U10](02-user-quotes.md#o-u10)
- 助手一度把基本知识复用收缩得过多，用户随后补充：需要类似 Pages／Blocks 的地方存手动收集的内容，再在 daily note 引用。自动抓取可以暂缓，基本存放和引用不能一并消失。[O-U11](02-user-quotes.md#o-u11)
- “未来列表代替完整 Calendar”“首版不接 e-ink”“打开页面才生成”“首版不发提醒”等主要是助手为降低成本提出的取舍，不能直接写成用户不需要这些能力。尤其 review 提醒是原始愿望之一。[历史范围稿](history/mvp-v0.1.md)

## 需要精确区分的来源

用户原话要求类似 Pages／Blocks 的内容存放，并在 daily note 中引用。原话没有逐项指定“必须同时提供整页和具体段落引用”“反向引用列表”“单层 Block”“每个对象怎样分表”。这些是助手后续将需求变为规格时提出的具体设计。评审可以评价或修改它们，同时说明如何继续满足原始存放与引用目的。[O-U11 原文](02-user-quotes.md#o-u11)

同样，独立 Task 身份、DailyPlacement、最多 3 条接续、撤销的版本条件、事务／RPC 等是为实现提出的规则。它们可能有技术价值，但不是每一项都已有用户原话确认。

“真实承诺不能静默消失、截止仍保留”在早期讨论中主要由助手作为可靠性边界提出；用户直接表达的是积压和操作负担问题。团队需要保留来源区分，再判断哪些边界合理。[原始聊天](sources/discussion-2026-10-13.md)

## 尚不能从聊天得出的事实

没有找到用户真实 daily note 样本、具体 review 习惯、常用设备分工、每天数据量、离线需求、通知偏好、模型预算和数据发送范围的完整答复。聊天中的任务、申请、会议与资料例子多数由助手举例，不是用户真实行程。

也没有真实产品使用、编辑器可行性或 AI 正确率的验证证据。文档完成、纸面推演和团队共识各有用途，不能互相替代。
