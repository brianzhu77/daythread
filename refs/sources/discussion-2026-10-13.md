角色：助手 · 2026-10-13 22:48:56 PDT · UTC `2026-10-14T05:48:56.910Z`

这三个场景把产品的主线说清楚了：**让系统记住尚未结束的事情、整理已经收集的信息，并在合适的时候把它们带回你面前。** 这样才能真正减少每天重新回忆和规划的消耗。

我建议围绕一个日常循环来设计：

**白天记录 → 晚间引导 review → 生成次日计划草稿 → Dashboard 呈现重点 → 根据实际进展继续调整。**

你提到的三个需求，分别在这个循环里承担不同的作用。

1. **Daily note：连接每天的行动**

   系统需要持续跟踪未完成事项，同时保留每天的记录。例如，一件事连续三天没完成，review 时可以引导你判断：继续推进、延期、等待别人，还是已经不值得做了。

   我建议未完成事项先进入“待安排”的范围，再结合 review 生成次日计划草稿。这样既能避免漏事，也能避免每天的计划被旧任务越堆越满。自动安排到什么程度，我们再根据你的习惯决定。

   Review 的价值也不只是勾选完成状态，还包括发现：今天为什么没推进、下一步是否足够明确、明天有什么值得优先做。

2. **知识库：让收藏重新进入使用场景**

   收藏之后，系统可以整理摘要、观点、来源，以及它可能适用于什么事情。但真正需要验证的是：**这些内容什么时候再次出现，才会对你有帮助。**

   比如，你准备做一个 app 时，之前收藏的相关 GitHub 项目能被找出来；某个任务一直拖延时，一段相关笔记能帮助你重新思考。这里的关键需求，是让收藏和当前的项目、问题、行动建立联系。

3. **Dashboard：呈现当下需要的少量信息**

   你的 e-ink 屏幕可以作为一个日常可见的出口。初步可以分成三块：

   - **今日 Top 3**：今天最想推进的三件事。
   - **需要留意**：待办、临近期限、等待跟进的事项。
   - **此刻有用的一条内容**：与当前处境有关的 quote、笔记或资料提示。

   这里还要逐步明确选择规则，例如 Top 3 由你决定、系统建议，还是两者结合。“实时”具体需要更新到什么程度，也可以等使用流程明确后再定。

**我建议先把 daily note → review → 次日计划这一段聊透。** 它会为知识库的内容推荐、Dashboard 的事项选择提供依据。

先从你已有的习惯开始：**你现在 Notion 里一天的 daily note 大致长什么样？** 可以贴一个去掉隐私的例子，或者用几行描述结构，保留你平时真实的写法就好。

角色：助手 · 2026-10-13 22:57:12 PDT · UTC `2026-10-14T05:57:12.812Z`

这个构想能形成完整的日常流程。压力测试后，我认为最需要设计清楚的是：**系统如何把一次随手输入，变成你能信任的未来安排，同时让主页保持清爽。**

“自动归类”只是第一步。用户真正需要知道的是：它理解了什么、准备什么时候再呈现、理解错了怎样改。

下面都是产品建议，尚未当作确定需求。

**先推演一次完整使用。**

你在主页输入：

> 这个 GitHub 项目好像适合我的 app，下周三讨论之前试一下：https://…

这句话同时包含一份资料、一个待办，以及一个时间约束。系统应该分别处理，并保持关联：

- 保存链接，开始获取和整理内容。
- 记录“试用这个项目”的待办，关联该资料。
- 识别“下周三讨论之前”的时间要求。
- 给出简短回执，例如：“已记录试用事项，需在 10 月 21 日前完成；链接正在整理。”可以直接修改或撤销。

如果系统不知道讨论的具体时间，就保留已知信息；如果没有一条对应的会议记录，也不应该凭空新增会议。

到了合适的时候，这个事项回到主页，旁边已经有项目摘要、你收藏它的原因，以及相关笔记。完成后，试用结论又能进入知识库。这样，收藏才有机会转化为实际使用。

**产品可以按这五步持续运转：**

1. **接住输入。** 先保存你的原话，再提取事项和资料。一段输入允许产生多个关联内容，TODO、Events、Notes 是查看方式，不必强迫每段话只能属于一类。
2. **展示理解结果。** 明确的信息直接记录；不确定的地方保留为未安排或待澄清。你能看到具体日期，也能用“改成周四”“这只是个想法”来纠正。
3. **安排再次出现。** 根据执行日期、截止日期、准备时间和跟进时间，把事项带回主页，并说明出现原因。
4. **支持处理。** 完成、延期、等待、取消都要有清晰的结果。Calendar、主页和 e-ink 展示的是同一件事的当前状态。
5. **通过 review 收尾。** 晚上处理悬而未决的事情，生成次日计划草稿。即使跳过 review，事项仍然保留，之后可以恢复整理。

最容易出问题的地方，我会这样测试：

| 压力场景 | 容易出现的错误 | 建议的产品行为 |
|---|---|---|
| “以后也许可以学画画” | 自动变成待办，每天催促 | 保存为想法，等待你决定是否行动 |
| “周五前交，周三开始准备” | 只识别一个日期 | 分清开始处理与截止时间 |
| “过阵子看看这个项目” | AI 随意挑一天 | 留在未安排事项中，可在 review 时重访 |
| “会议改到周四” | 新增一场会议，旧的还在 | 更新明确对应的事项；多个候选时再询问 |
| 一条链接获取失败 | 看起来已入库，实际没有内容 | 保留链接，明确显示失败或只获取了部分内容 |
| 收藏文章里有行动清单 | 文章内容变成你的个人任务 | 作为资料整理，个人承诺来自你的表达 |
| 连续十天没打开 app | 今天堆满几十条旧任务 | 先呈现重要期限和已安排事项，其余汇总待整理 |
| 昨天的日记写“我什么都做不好” | 被写成长期个人画像 | 保留当时的感受，避免固化成关于你的结论 |

其中最值得提前解决的是下面三个问题。

**第一，daily note 需要保存历史，事项需要持续更新。**

假设周一记录了一件事，周二延期，周四完成。你应该既能看到周一的原始记录，也能知道它现在已经完成。

因此，我建议把“每日记录”和“跨日事项”联系起来：每日页面记录当天发生的事情，持续存在的事项记录当前状态。这样不会每天复制出一个新任务，也不会因为改期而抹掉过去。

**第二，“逐步回到主页”需要一套你能理解的规则。**

比如一件月底截止的事情，可以经历：

> 进入准备窗口 → 出现在近期关注 → 到计划执行日进入今日安排 → 临近截止时加强提示。

提前多久不能全部统一：预约、提交材料、阅读文章的准备周期不同。最初可以由你指定，再逐渐形成个人默认规则。

同时，**主页出现和主动通知应该分别控制**。值得看见的内容很多，值得打断你的内容应当更少。

**第三，主页必须控制容量。**

我建议主页优先呈现：

- **今天**：既有日程、选定的行动、Top 3。
- **需要留意**：临近期限、等待跟进的事情，并解释为什么出现。
- **输入与今日记录**：随手写东西的入口和当天记录。
- **此刻有用的资料**：少量关联内容，没有合适的就留空。

未安排事项、收藏和历史记录都有自己的去处。否则，主页很容易随着使用时间变成另一个需要整理的收件箱。

对于自动化程度，可以考虑三种方式：每条确认、全部自动、按情况确认。**我建议按情况确认：明确表达直接记录并给回执；模糊表达先保留；涉及不确定日期、对象或改动时再问。** AI 推荐的今日计划保持为草稿，方便你调整。

第一版最值得验证的是这一条闭环：

**随手输入 → 可靠记录 → 按时回到主页 → 完成或调整 → review → 次日计划。**

再让收藏资料沿着这条流程被重新使用。验证时可以拿真实三天的 daily note 来模拟，重点看需要纠正多少次、是否漏事、返回时机是否有帮助。我已把这些推演整理进[产品压力测试稿](/Users/dogrod/Documents/Codex/2026-10-13/wo-j/outputs/product-stress-test.md)。

接下来有一个会影响整个产品体验的选择：**你希望打开 Home 时，首先看到“今天的行动安排”，还是首先进入“今天的自由书写页”？** 两者可以共存，但需要确定哪个是主入口。

>

> - 哪些未完成事项需要重新安排？

标题、段落、顺序、内容都可以修改。这个结构也应当逐渐适应你的习惯。

但要让它长期好用，需要明确三个行为。

**1. 页面可以自由编辑，里面的事项仍然能被跟踪。**

你勾选完成，关联任务随之完成；你把“周三提交”改成“周五提交”，系统显示日期变更，Calendar 和未来提示随之更新。

普通日记也可以自由写。像“今天不想做这个了”这样的感受，不应直接触发取消任务。系统需要区分书写与明确的操作意图。

**2. 系统起草之后，后续更新要尊重你的编辑。**

我建议每天先生成初稿。你开始编辑后，新发现的事项、改期和资料推荐，作为简短的“可加入今日页的更新”出现，由你合入。你也可以主动要求“根据现在的进度重新整理剩余计划”。

否则，你上午认真调整过的页面，下午可能又被系统重新排了一遍。

**3. 今日页既记录当时的计划，也保留实际发生的变化。**

到了第二天，系统根据事项的最新状态生成新页面。昨天的日记和回顾留在昨天，未完成事项保持关联，再决定是否进入今天。这样以后回看时，你能知道当时怎样计划、后来发生了什么。

对 dashboard 也有好处：你在每日页里选定的 Top 3、安排和任务状态，可以直接成为 e-ink 的展示来源，减少重复维护。

这里最需要先确定一个编辑规则：**如果你从今日页里删掉一条未完成任务，你希望它表示“今天不做”，还是“这件事取消了”？** 我倾向默认理解为“移出今天”，保留到未安排事项里；取消则用一个明确操作。

结合你的每日建议页，我倾向下面这套交互。它是基于这些机制提出的设计建议。

**1. 一个动作“暂放”，当下不选去向。**

任务行旁边提供一个轻量操作，也可以用滑动或快捷键。执行后只出现短暂反馈：

> 已暂放，今天不再推荐。　**撤销**

不弹日期选择器，也不问“明天／下周／以后”。需要精确安排时，你仍然可以直接写“周五再做”，但这属于主动操作。

如果你在文档里删除整条任务行，也可以采用同样的默认行为。

**2. 系统需要区分“建议你做”和“你已经决定要做”。**

这是控制积压最关键的一步，而且大部分可以利用已有操作来判断：

- **系统推荐、随手想法、收藏后的潜在行动**：暂放后降低重现频率，多次暂放后退出主动推荐，仍可搜索或从关联项目中找回。
- **你明确创建或主动选入计划的任务**：保留未完成状态，暂放只影响今日安排。
- **有截止日期、固定日程或明确提醒的事项**：保留原有时间约束。移出今日计划时，用行内反馈说明“周五截止提醒仍保留”，无需弹窗。

这里不能把“没做”直接解释成“不重要”。没有截止日期的事情，也可能是你的真实承诺。

**3. 给暂放留出间隔，避免明天又原样出现。**

例如，你把“试用一个 GitHub 项目”暂放了：

- 今天从建议页消失。
- 明天不因为“还没完成”就自动塞回来。
- 当你再次推进相关项目，或者主动寻找替代工具时，它才有理由重新出现，并说明关联。
- 对没有明确触发条件的可选事项，可以在低频回顾里少量呈现。

这比每天自动顺延更符合“我现在不想处理它”的意思。**明确暂放是反馈；单纯没有勾选完成，不应自动视为拒绝。**

**4. Review 按主题整理，减少逐条决策。**

例如一周后，系统发现你暂放了几项相关探索，可以在 review 里给一条汇总：

> 这周有 4 项关于个人 app 的探索被暂放，仍保存在项目里。  
> **展开看看**

你不展开，它们继续保留，不要求你完成四次分类。只有真实承诺出现冲突、期限临近，才需要更明显地带回来。

这里还有一个能从源头减少积压的设计：**“收藏一个链接”默认产生资料；只有你表达了行动意图，才产生待办。** “这个不错”可以作为笔记，“下周试一下这个”才需要跟踪。否则知识库越丰富，待办反而越多。

所以，我推荐的默认体验是：

**一步暂放 → 即时可撤销 → 今天保持清爽 → 可选建议降低重现频率 → 明确承诺继续被跟踪 → 有相关情境时再找回。**

它不能替你消除已经答应要做的事情，但能避免把每个灵感、每次收藏、每条 AI 建议都变成需要偿还的任务。
