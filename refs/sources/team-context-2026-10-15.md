| Agent | 职责 | 初始 Runtime |
|---|---|---|
| **Lead：产品与协调** | 理解你的目标、维护计划、拆任务、分配工作、汇报阻塞 | Claude Code |
| **Builder：开发** | 阅读代码、实现功能、补必要测试、提交可审查的改动 | Codex CLI |
| **Reviewer：审查与验证** | 检查实现是否满足需求、复现问题、验证关键流程 | Claude Code 或 Codex CLI |
| **Designer：体验设计，按需加入** | 梳理用户流程、设计页面、检查交互和视觉 | Claude Code |

这个配置是起点，后续按实际产出调整。Raft 支持同一团队混用不同 Runtime。[官方说明](https://docs.raft.build/features/agents/runtime/)

协作流程建议固定下来：

**你提出目标 → Lead 写验收标准 → Builder 实现 → Reviewer 验证 → 你体验并决定下一步。**

落地时抓住四件事：

- **一个主频道，每个功能一个任务线程。** 决策和交付结果留在对应线程里。
- **每项任务写清负责人、交付物、验收条件和依赖。** 避免只有“优化体验”这种无法判断完成的描述。

- **并行开发用独立分支／worktree。** Reviewer 根据具体提交验证；起步阶段同时只推进一个功能，先观察整个流程能否完成。

第一次试运行，我建议选一个你能亲自体验、能明确判断好坏的小功能，让团队交付完整结果。这样能尽早发现问题究竟出在需求、实现还是交接。

建议采用 **3 个核心角色 + 按任务参与的 Designer**：

| Agent | Runtime 建议 | 负责什么 |
|---|---|---|
| **Lead** | Claude Code | 守住已有范围、拆任务、协调依赖、汇总交付 |
| **Engineer** | Codex CLI | 贯穿前端、领域规则、Supabase 和 AI 接入 |
| **QA** | Codex CLI | 针对明确提交独立验证，重点检查日期、引用、保存与冲突 |
| **Designer** | Claude Code | 前期确定核心交互，后续审查真实页面体验 |

现阶段先由一名 Engineer 贯穿完整功能。Daythread 的编辑器、稳定 Block ID、任务状态和数据库写入关联很紧，过早拆成前后端团队会增加交接成本。

第一轮按这个顺序：

1. **建立基线**：初始化 Git，保留现有规格，明确各成员工作目录。
2. **设计与验证并行**：Designer 梳理今日页、资料页、引用和 review；Engineer 验证编辑器的稳定 ID 与自有块；QA 准备验收。
3. **交付第一个可体验切片**：保存资料页 → 刷新后恢复 → 今日页引用整页／段落 → 点击定位原文 → 查看反向引用。
4. **接上事项与日期**：完成、改期、暂放、未来回流，保证跨日不复制任务。
5. **接上真实 AI 与每日闭环**：自然语言录入、草稿、review、次日接续，再进入 5–7 天真实试用。

Raft 里先用一个 `#daythread` 频道，每项工作建成顶层 Task，讨论和验收留在线程里。每项任务指定负责人、审查人和现有验收编号；写代码的成员使用独立 worktree。Raft 默认从各 Agent 自己的 workspace 启动，需要明确告诉它们项目工作目录。[Workspace 说明](https://docs.raft.build/features/agents/workspace/)

**你现在可以先创建这四个角色，粘贴配置包中的共同指令与角色指令，再把第 8 节启动消息发给 Lead。** 第一轮只激活前五项任务，让团队先交付一个你能亲自用的完整结果。
