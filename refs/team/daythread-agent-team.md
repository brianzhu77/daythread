## 本轮各角色的任务

以下是评审重点，成员可以提出职责之外的发现。

| 角色 | 值得优先回答的问题 |
| --- | --- |
| Optimus Prime（Lead） | 材料有哪些矛盾与未决点？哪些结论需要依据？怎样让评审产出可执行决定，避免重复已有讨论？ |
| Bumblebee（Product） | 最主要的日常痛点和价值是什么？两条循环如何相互支持？现有 MVP 范围是否适合验证价值？哪些功能或规则应增减、调整或做实验？ |
| Jazz（Designer） | 自由书写、事项操作、引用、日期提示和 review 是否能形成易理解的体验？一步暂放与低维护负担是否成立？是否有更简单的交互？ |
| Wheeljack（Engineer） | 当前对象、日期／状态语义、编辑器与数据库映射、原子写入和 AI 边界是否可行且适度？技术偏好有哪些兼容性、成本和交付风险？哪些需要实验？ |
| Ratchet（Reviewer） | 现有验收是否覆盖主要风险，是否把未验证假设写成要求？如何证明数据不丢、引用和日期正确、实际使用有价值？还缺哪些验证？ |

所有人先基于同一份材料形成独立意见，再交叉讨论。现有验收编号可以引用，但验收标准本身也在审核范围内。

## 建议形成的结果

一个集中的评审包即可，不按角色堆积大量重复文件：

1. 产品与技术现状、材料版本、已知证据及缺口。
2. 建议保留／修改／删除／暂缓／验证的内容及理由。
3. 重要分歧、有实质区别的替代方案与推荐。
4. 最小必要实验，例如编辑器稳定引用与保存映射、关键流程原型；是否需要实验由评审结论决定。
5. 修订后的产品与技术方案建议，以及仍需用户判断的问题。
6. 基于评审结果的实施任务、依赖和验证标准。

本轮以评审与修订为目标，正式应用实现留给后续实施任务。必要的小型原型或技术实验标明目的和结论，避免演变成未经评估的大规模实现。评审报告不能声称用户已批准修订建议。

## 接手时的优先级

用户最新反馈 → 本次项目评审目标 → 历史用户表达与已获得证据 → 当前草案。不同来源冲突时指出冲突，不能用旧文档覆盖最新要求。
