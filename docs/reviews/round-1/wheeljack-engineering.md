## 判断

两条循环值得验证，但现有首版同时建设编辑器、事项系统、资料引用、AI 操作协议和历史恢复，建设顺序让最关键的每日价值到 M4 才出现。推荐保留两条循环，改成先验证最危险的接口，再做一个贯穿录入、明日回流、资料引用和 review 的窄切片。框架不需要重选；更换框架不能消除状态语义问题。

最新用户消息将 TanStack Start + TS、Supabase、OpenRouter + GPT 定位为历史偏好，旧文档却写成已确定。推荐保留为默认候选并改正措辞，只有验证出现实际阻碍才提出替代。目标是减少规划与 recall 消耗；Page/Block 表、3 条候选、动态历史引用、BlockNote 都是当前设计或假设。

## 已有基础与范围

当前只有七份规格，无可复用应用代码，不能把纸面错误处理计作已验证能力。已有材料对稳定身份、日期与时区、Capture 先存、原子应用、条件撤销、RLS 的方向合理，建议复用。JSON 导出优先于 Markdown 合理，但不等于备份恢复。

不在本轮范围：正式应用、远程部署、生产数据库写入、向量检索、后台 worker、自动抓取、协作与 CRDT。理由分别是用户限定评审阶段，以及尚未证明这些复杂度是核心循环的瓶颈。

## 1. 高优先级：一个任务有三处安排来源，必须定义一致性

证据：02 的 Task.planned_on、DailyPlacement 与正文 task Block；01 F03/F06 支持普通编辑删除任务行，02 又允许同日重复引用。缺少“普通引用”和“当日安排块”的机器可区分字段，以及改期后旧页面和 placement 的处理。

复现场景：今天安排 A，改到明天，返回今天的正文仍显示 A；或同日引用 A 两次，删除其中一处触发全局暂放，另一处仍可勾选。按现有文字不能唯一决定结果。更危险的是未来页提前含有 A，之后改期却保留 included，可让旧日接续错误回流。

推荐：Task 是事项事实的唯一来源；DailyPlacement 是该日选择记录；Block 只是呈现。为任务块明确 placement / ordinary-reference 两种用途。所有安排操作用一条事务同时更新 Task、受影响 placement 和正文关联；旧页正文可保留引用，但标示已改期，不参与接续。删除普通引用永不改安排；删除当日安排应是显式“暂放”，键盘删除不能静默升级为取消承诺。相较删除 DailyPlacement，这保留用户排除意图，代价是必须写清转换表。

最低验收：同日重复引用、今日→未来→今日改期、提前创建未来页后再次改期、历史页删除、普通资料页删除、取消后恢复六组场景，检查同一 Task ID、所有安排关系和下一次候选结果，而不只检查当前屏幕。

## 2. 高优先级：最近计划算法会吞掉仍需接续的任务

证据：02 接续候选只读 D 前最近一份有效每日计划；建议展示不更新 planned_on；候选最多 3 条。

反例：周一 A 未完成，周二只有自由笔记或候选未合入，周三最近页是周二，A 是否仍有资格没有定义。连续几天只取 3 条，后排候选也可能永久丢出接续集合。另有 planned_on 已过期却不在最近页的任务，既没有截止提示也可能不再出现。

推荐：定义确定性的 carry frontier（仍可接续的事项集合），由未完成且未暂停、无未来安排的用户选择事项产生；按最后明确安排时间与稳定 ID 排序，展示最多 3 条不移除其余资格。无需新建队列服务，可用查询或轻量关系表达。若产品坚持只接续最近计划，必须明确这是主动舍弃较早候选并提供可发现入口，不能声称“不漏事情”。代价：集合可能增长，需要产品验证展示负担；隐藏集合不等于解决积压。

验收：空白日、只有笔记日、连续跳过三天、超过 3 条且连续暂放一条、提前建立未来页，均检查候选资格与展开入口。

## 3. 高优先级：资料与指令不能只靠模型标签区分

证据：03 要求将本次指令、资料、历史、AI 内容分别标注；但 F02 的同一自然语言入口又能自动创建/完成/改期事项。一段带命令的粘贴文本究竟是资料还是用户操作，没有确定性边界。结构 schema 与 evidence 只能验证形状/来源存在，不能证明用户授权某个含义。

推荐默认：Pages 粘贴路径强制 source-content，禁止状态操作；自然语言 capture 为用户输入，但引用/粘贴的大段正文保持 source-content。首次对既有事项的完成、取消、批量改期等提案先显示可撤销的差异确认，明确新任务可按回执自动创建。若坚持全部自动应用，则把错误动作率与纠正成本作为首要实测，而不能把 X08 的单例通过当成安全保证。这个自动应用程度是产品取舍，交给 Lead 综合。

最小模型实验：20 条固定输入，覆盖明确动作、感受、条件句、转述、否定、两场同名会议、文章清单和恶意命令；每条记录期望对象/字段、模型提案、实际错误、纠正次数。重复执行至少一次观察波动。无凭证时只交数据集与方法，不宣称通过。

## 4. 高优先级：幂等必须包括输入版本、并发领取与部分成功

证据：Capture 可以编辑并 supersede；03 澄清仍沿用 Capture；05 中断后重试；Review 应用与草稿分别幂等。但尚未定义 idempotency key 的作用域、同 key 不同输入，以及 running 请求失联后的恢复。

推荐：capture_id 保留原始录入身份，capture_revision 每次原文/澄清更新递增；attempt_id 表示一次模型尝试；apply_key 唯一约束绑定 capture_id+revision+mode。事务检查当前 revision、目标版本与 apply_key，并写 Change 和最终结果。相同 key 不同 payload 明确拒绝。processing 有 started_at/lease_until，超时允许重新尝试；允许重复模型费用，但只应用一次。不要为此引入后台 worker。

Review 明确显示三个独立阶段：原话已保存 → 变更已提交 → 明日草稿成功/失败。草稿失败只重试生成，不能再次完成/改期。ready 不是 saved/applied。空页是否已生成也必须靠状态判断，不能靠正文是否为空，否则用户删光正文会反复触发生成。

验收：两请求同时应用、旧 revision 晚到、响应丢失后刷新、同 key 换文本、变更成功但草稿失败、用户主动清空已生成页。故障注入验证事务，而不是仅测试模型假返回。

## 5. 中优先级：编辑器映射应先做可丢弃实验，不能直接锁死逐块保存

证据：05 选择 BlockNote 建议、单层 Blocks 为唯一正文，并要求版本差异保存；没有验证 split/merge、跨页粘贴、撤销和实体状态之间的接口。

官方文档证明可以定义自有块，不证明本项目的稳定 ID/保存/撤销协议已经成立。尤其原生撤销可能恢复已删 task 块，却不应回滚其他页面刚完成的 Task。

推荐先比较两种适配成本：A，逐块记录+页面结构版本；B，每页一个带稳定 Block ID 的规范 JSON，Task/Event 独立，通过事务提取引用索引。B 降低编辑事务复杂度，但搜索/反链需索引投影，页面级冲突更粗。默认先试 A，不在无实验前承诺它比 B 简单。两者都只能有一个正文真源，不双写两份独立正文。

实验只做两个页面和 task/reference 块，执行中文输入法、Enter 拆段、Backspace 合段、移动、复制粘贴、删除/恢复、刷新序列化、实体完成后编辑器撤销。记录哪些 ID 保留、哪些产生新身份，确保重复粘贴产生新 Block ID 且引用仍指向原 Task。若无法稳定限定单层，选更轻编辑器或接受小范围嵌套，不能靠规格假装禁用已生效。

## 6. 中优先级：完整工作区上下文不是零成本默认

证据：03 每次送 workspace_content，包括所有正文、Capture、review；X11 只规定超容量后失败。手动资料可迅速使每日最核心入口无法工作，而且在达到上限前就有延迟、重复费用和敏感信息外传量。

推荐保持简单，不建检索系统；至少测量上下文字节/token 估计、模型耗时、用量与每次调用费用，并设输入/输出预算与超时。基准数据包括 10/50 篇资料及连续 7 天计划；具体费用依选定模型实际用量核算，不预报未经测量的价格。超过预算应先告知并保留原文，允许用户明确缩小到当前页+日期事实+手选资料；这相对“已有信息直接交 AI”的历史偏好是建议修订，不能暗中裁剪。

输入版本应只绑定提案真正读取/修改的实体和目标页结构，避免任何无关笔记编辑都使整份工作区草稿失效。日志只记录请求 ID、阶段、耗时、用量与错误类型，默认不复制全文到第三方日志。

## 7. 中优先级：访问隔离需要数据库约束，不只依赖服务端检查

证据：02 已要求 workspace_id、调用者权限 RPC、RLS，这是正确方向。待补的是同工作区关联的可执行约束与函数权限清单。

推荐为目标关联使用 workspace_id+id 复合唯一/外键约束；引用目标不可跨 workspace，RPC 验证所有入参目标。撤销、导出、搜索、反向引用和 AI 上下文读取都纳入同一权限矩阵。安全调用者权限函数无需为 convenience 提升；若确需 definer，固定 search_path、限制 execute 并显式验证 auth.uid。Supabase 文档支持上述权限模式，但项目尚无 SQL 可验证。

验收：两个测试用户，互换 workspace/page/block/task ID，经普通查询及 RPC 都拒绝；篡改 source ID、嵌套引用、导出和搜索也不能泄漏。不要只验证未登录页面跳转。

## 推荐处理流与失败检查

```text
保存 Capture(revision)
    → 领取 attempt（可过期）
    → 读取带权限与版本的上下文
    → 模型返回提案
    → schema + ID/权限 + 日期校验
    → 差异确认（需要时）
    → 数据库事务[revision + versions + apply_key]
    → 事实/placement/引用/Change + 持久结果
    → UI 按已提交结果生成回执
```

未来实现应把此图放入 captures 服务旁，事项转换表放在领域模块旁。

| 路径 | 现实失败 | 现有覆盖与缺口 | 推荐验收 |
| --- | --- | --- | --- |
| 自动保存 | 会话过期/两个标签页竞争 | 有通用文案，无保存顺序协议 | 页面结构 revision CAS，保留本地未保存文字 |
| 模型尝试 | 超时后服务进程退出 | 有失败入口，无 running 恢复定义 | lease 过期后可重试 |
| 原子应用 | 并发或响应丢失 | S03/X03 有方向，无 revision/key 约束 | 数据库双请求与断响应实验 |
| 草稿合入 | 生成时用户开始输入/删光页 | R06 有覆盖，空页重复生成缺口 | 按 Generation 状态与页版本检查 |
| 编辑器 | 撤销恢复了旧实体状态 | 无明确覆盖 | 编辑器撤销只改呈现；实体撤销走 Change |
| 引用 | 目标软删除/跨工作区 | P06/S02 有意图 | 数据库约束与渲染占位分别验证 |
| 跨日 | 空白日吞掉旧任务 | R05 不能唯一确定算法 | 多日状态序列表 |

以上均是规格覆盖评估，没有执行应用测试。当前不存在可验证的异常处理代码，不能给出运行通过率。

## 最小验证与后续任务（建议，未经创建或实施）

1. 领域状态表与纯数据夹具：统一 planned_on / placement / Block，验证跨日与候选反例；交付输入/动作/结果表，可由 Reviewer 独立推演。
2. 编辑器可丢弃实验：只验证稳定 ID、持久化往返、实体块与撤销；不做完整界面或云端部署。
3. 数据库可丢弃实验：本地 Postgres 或隔离 Supabase 测试环境，测试双请求、revision、同工作区关联与两用户权限；不得对正式数据执行。
4. 真实模型小样：在凭证与预算具备后执行上述 20 条数据集，同时记录上下文增长；与 1/2 可并行，结果交叉审查。
5. 先贯穿一个“录入明日任务+资料 → 明日打开 → 引用资料 → 完成 → review”的窄切片，再扩展完整编辑器和回收站。正式实现仍需本轮综合修订完成及后续授权。

并行安排：领域模型负责人独占数据/状态文档；编辑器实验独立目录；模型实验独立目录；SQL 必须等待领域表稳定。之后应用领域/数据库层与页面适配层可并行，但共享 schema 由一人维护，避免并行改同一协议。

## 只能由 Brian 决定的问题

- 自动应用对现有承诺的改期/完成/取消，愿意承担多少纠正风险？推荐先确认差异，日常明确新任务自动创建，交 Lead 判断是否需要上呈。
- 实际常用设备与可接受的联网依赖；若希望手机随时录入，本机运行不是等价交付。推荐先验证常用一台设备，不假定要离线应用。
- 可接受发送到外部模型的资料范围与试用调用预算；没有授权前不执行付费实验。

其余如版本号、幂等键、数据库约束和单应用结构可由团队给推荐值，不需要用户逐项批准。技术栈偏好暂保留，不为评审强行重选。

## 我会做的最小实验

本轮可做的最小实验是十余步纯数据状态推演，验证旧计划→笔记日→回归、提前创建未来页再改期、同日重复引用再暂放，输出明确的预期状态表；不以模拟证明数据库原子性或模型准确性。编辑器与数据库可丢弃原型、真实模型数据集执行只列后续验证任务，遵守 Lead 当前不写应用代码/不装依赖/不建项目/不调用付费 API 的边界。

## 首轮我会砍掉的内容

- 不建通用富文本编辑平台、完整逐块差异合并、协作同步；先用页面级 CAS 保留双方内容，再按真实冲突决定细粒度合并。
- 暂缓 AI 自动发现跨全部资料的关联与任意批量动作，先保留手选引用及明确输入提案；资料保存与稳定引用仍保留。
- 暂缓 Markdown 导出、复杂回收站界面、完整历史快照；保留 JSON 导出、软删除恢复入口与关键事项 Change。
- 不先完整实现旧 M1 再等 M4 验证每日价值；改成窄切片，避免编辑器建设先消耗全部预算。

1. **当日唯一来源：有条件支持 Jazz A 作为推荐原型，调整我原先偏向正文模型的默认。** A 让安排来自 Task 与当日选择/排序，Notes 只存文字与引用，少一套“把安排合入正文”的协议，工程复杂度确实更低。但仍要区分“今天做”“期限事实”“候选”，不能把已暂放截止项呈现成今日承诺，也不能消除所有草稿与人工编辑冲突。底线：同一事实一行、多日期用标签，普通引用删除永不改事项，安排用明确操作。A 不能因工程省事就被宣布满足自由每日页偏好；A/B 验证 Brian 是否需要计划与文字交错，若需要则选 B 并承担安排块协议。

2. **接续：同意一套库存查询、多个轻量呈现，补充无日期新任务。** 我原 frontier 只覆盖曾安排事项，不够完整。采用 Ratchet 的查询：open 且无未来计划日的任务持续可发现，无日期新任务也在内。自动接续只从未暂停且曾明确安排的子集取最多 3 条，稳定排序；其余在 Bumblebee 折叠“仍未完成”入口展开，未曾安排标“未安排”，暂放单独筛选且不自动推荐。截止/关注事实独立有效。底线：上限只限展示，不删除资格，不建三套持久库存、不要求清零；轮换排序等观察后再考虑。

3. **打开页 AI：同意去掉自动调用，与次日草稿不冲突。** 确定性事实即时打开；review 产生明日建议，跳过 review 后可主动“准备今天”。底线：建议不能修改权威日期或覆盖 Notes，没有 review 仍能用。若保留主动准备，daily_draft 协议与版本校验仍存在，省掉的是自动触发及高频竞争，并非整个生成系统。

4. **资料：有条件接受 Bumblebee 的 0–2 条推荐试验，调整我完全暂缓的建议。** “收藏后不回看”使纯手选引用难以验证 recall 改善，应测被动找回。但全工作区已送模型不等于零成本，仍有噪声、容量与发送范围问题。底线：仅从用户允许的有限资料集推荐，允许 0 条，每条真实 ID 与一句关联理由，不自动插正文或建任务，先人工回放看是否帮助行动。页面级引用可作窄切片，保留稳定 Block ID，块级定位/反链 UI 后置；不能把页面级切片算作旧 P03/P13 全通过。若真实使用需要摘录定位再恢复范围，无需重建正文身份。

5. **已有事项确认：同意 AI 提案默认，反对扩展到直接 UI 操作。** capture/review 修改已有承诺先给一份差异摘要；新建可自动应用并给可编辑回执，歧义或批量粘贴仍预览。直接勾选 Done、选日期、按暂放，本身已是明确操作，不再弹确认。底线：确认时重查对象版本与原文 revision，确认按钮不能使旧提案永久有效。

6. **验证顺序：同意状态回放与低保真 A/B 并行，反对全部串行为数周前置门槛。** 共用脱敏或合成案例；回放验证规则唯一、原型验证理解。Brian 同意真实材料、时间和模型使用后，4–5 天 concierge 可并行；不强制先做 3 天新基线，可从已有样本给粗基线并标限制。编辑器实验等 A/B 选定且切片仍需块级交互再做；若选结构化 A 与页面引用，砍完整自有 task 块实验，先试薄文字/引用保存。底线：人工代理不证明应用一致性，纸面推演不证明数据库事务。

**其他阻断级补充：不新增一项，但限定范围削减底线。** 可砍复杂合并和全局撤销 UI；不能因单用户而砍版本冲突检测与条件撤销前置检查，两标签页及重复请求足以覆盖数据。JSON 导出不等于恢复能力。Bumblebee 的 3 次资料复用、每天少于 2 次回旧工具等阈值是候选观察标准，在未知基线时不应成为已有效的默认门槛；核查、确认、手动同步时间都计入总负担，并允许证据不足。

推演发现的待明确项：

- pool 定义没有未来计划日，天然包含今天已 included 的任务；“曾安排过”不足以阻止它再次成为今日建议。应在候选层明确排除 today included、done/cancelled，并按 Task ID 与日期事实去重。
- 暂放当天只清除 planned_on 等于当天的日期，因此旧计划日可能保留（步骤 5）。需要说明过去日期是历史安排，不等于逾期，也不绕过暂停。若改成一律清旧计划日，要作为明确规则修订同步撤销前值。
- B 有 attention 又有 deadline 且 paused 时，必须同一事实行优先截止标签，不能一边将关注折叠、一边遗漏截止；pool 数量不应混入 paused。
- 单独“撤销原子多对象操作”只检查对象版本还不够：后来新增引用也构成依赖。删除新建产物前应检查下游使用，否则用保留产物的恢复流程替代撤销。
