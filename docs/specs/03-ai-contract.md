# 03 · AI 契约

目标：用简单模型调用跑通录入、草稿和 review。用户已确定通过 OpenRouter 调用 OpenAI GPT 系列。这里约束可观察行为与数据安全性，不要求复杂 prompt、检索、多 agent 或自主工具执行。

## 输入上下文

试用数据量小时，直接提供当前输入和已有工作区内容。页面 ID、Block ID、任务/事件 ID、日期含义、版本与来源一起提供，不只拼接成无法定位的正文。

请求最少包含：

| 字段 | 作用 |
| --- | --- |
| request_id / capture_id | 对应已保存输入，支持幂等应用。 |
| mode | capture / daily_draft / review / selected_text。 |
| local_now / timezone | 日期解析基准，来自 App。 |
| active_page_id / active_page_date | 当前编辑位置与日记日期，区别于真实今天。 |
| base_versions | 相关对象的读入版本，应用前检查。 |
| input_text | 本次用户表达，和资料正文分开。 |
| workspace_content | 当前已存页面、基础块、任务、事件、review 与来源信息。 |
| daily_facts / carry_candidates | App 按日期和状态算出的事实与接续候选。 |

不做向量库、摘要记忆、多级检索或推荐排序。容量超出模型上下文时明确失败并保留输入，不静默截断后假装完整理解；这时根据实际试用再决定最小上下文限制方案。

## 三类职责

### 录入与明确操作

模型把输入转换为结构化变更提案，App 校验并保存。模型不能直接写数据库或执行任意代码。

可提出：创建/更新任务，创建/更新事件，新增笔记或资料页/Block，引用已有内容，明确取消/完成任务，明确改期或暂放。

不可直接执行：永久删除资料、批量清空、外部网络抓取、发送通知、修改工作区配置。需要删除页面时走正常 UI 操作。

### 每日草稿

基于真实日期事实与接续候选组织可编辑页面。既有安排必须引用原 ID。模型提出的新行动保持为建议文字，不创建新的个人承诺，也不推断已完成。

### Review

保存用户回顾文字，识别其中明确调整，再生成总结和明日草稿。回顾原文与生成总结分开。单句“太累了，不想做了”默认是感受，不取消全部任务。

## 结构化返回

返回要区分“可以应用”和“需要澄清”。下例是协议示意；字段与枚举在实现时固化为可验证 schema，不能仅靠自然语言回执决定是否成功。

```json
{
  "request_id": "request-1",
  "status": "ready",
  "operations": [
    {
      "op_id": "op-1",
      "action": "create_task",
      "temp_id": "new-task-1",
      "fields": {
        "title": "交材料",
        "planned_on": null,
        "attention_on": "2026-10-14",
        "deadline": {"date": "2026-10-16", "time": null, "timezone": "America/Vancouver"}
      },
      "evidence": "周五之前交材料，周三开始准备"
    }
  ],
  "suggestions": [],
  "clarification": null
}
```

规则：

- 新对象用临时 ID，真实 ID 由 App 分配，并在同一操作集合中解析引用。
- 更新必须给出已存在 target_id、expected_version、实际修改字段与本次输入依据。
- 模型给出的 ID、版本、日期和链接都需校验，不因为格式像 ID 就信任。
- 未提供字段表示不修改；显式 null 才表示清除可空字段。不能用缺字段清空截止日期。
- 不允许模型把无法找到目标的 update 自动降级成 create，避免改期时复制事项。
- 操作类型为受限枚举，每类只接受允许字段，超出的字段导致提案无效。
- 校验真实日期与时间范围；事件结束早于开始、用户表达自相矛盾等情况保留原话并澄清，不静默修正成另一天。
- evidence 是审阅线索，不能替代校验；App 的成功回执由实际提交结果生成。
- daily_draft 返回 Block 提案与已有对象引用，不能夹带未请求的状态变更。
- review 返回明确变更提案、单独总结与明日草稿；应用和生成各自有幂等记录。

存在影响对象/日期的歧义时：`status = needs_clarification`，operations 作为待定提案不应用；显示一个具体问题。用户补充后沿用原 Capture 继续处理，不创建另一份原始任务。没有可处理操作时保留为普通记录，不以模型“没有行动”作为错误。

## 信任边界

用户本次指令、历史用户记录、收集的资料与 AI 生成内容分别标注。资料里的命令句和日期属于资料内容，不能当成新的个人任务或操作指令。

用户粘贴的原文不被摘要替换。未提供正文的 URL 只保存链接，生成“未提供正文”的资料页；不得声称抓取、阅读或总结了该页面。首版没有浏览工具。

模型可以发现关联并提出引用，必须指向实际存在内容。没有依据时不生成来源或引用。

## 自动应用边界

| 情况 | 默认行为 |
| --- | --- |
| “明天下午三点开会”且日期明确 | 创建事件，时间和日期在回执可见。 |
| “周五前交材料” | 创建任务与明确截止；不额外编处理日。 |
| “以后也许学画画” | 普通想法，不建待办。 |
| “要给 Alex 发邮件，时间未定” | 创建无日期任务。 |
| “会议改周四”且仅一个明确候选 | 更新原事件，回执展示变更。 |
| “会议改周四”且有多个合理候选 | 保留原话，询问改哪场。 |
| 输入一份带清单的文章 | 保存资料，不把正文清单全部建为个人任务。 |
| 用户直接编辑普通日记段落 | 保存文字，不发起隐式操作。 |
| 用户主动“重新整理今天” | 给出可应用更新；不立即覆盖人工正文。 |

## 请求生命周期

```text
用户输入
  → 保存 Capture 和待整理位置
  → 请求模型
  → 校验结构/ID/权限范围/版本/日期
  → 原子提交或保留待澄清/失败
  → 根据实际结果显示回执
```

| 异常 | 处理 |
| --- | --- |
| 保存原文失败 | 不调用 AI；保留待保存文字，显示未保存。 |
| 模型超时/不可用 | 原文保持可编辑；可重试，也能手动建任务/事件。 |
| 返回非结构化或校验不通过 | 不应用操作；保留原话和错误状态，可重试。 |
| 已应用请求重试 | 返回已有结果，不再次建对象。 |
| 旧请求晚返回、原文已改 | 丢弃旧提案的应用资格，保留结果供查看或重试。 |
| 应用期间发生版本冲突 | 不覆盖新状态，重新核对相关内容。 |
| 本地编辑期间草稿生成完成 | 草稿进入待应用区，不替换正在写的内容。 |

## AI 接入完成的标准

真实模型完成录入、每日草稿和 review 三类调用，真实产物通过校验并持久保存，失败路径可恢复。供应商已确定为 OpenRouter，模型为 OpenAI GPT 系列，具体模型 ID 在运行环境配置。凭证不写入文档、导出数据或前端可见配置。

若使用演示数据/模拟模型，只能标记为交互演示，不能算 AI 功能验收通过。

## OpenRouter 传输约定

- TanStack Start 服务端函数使用 `https://openrouter.ai/api/v1` 和 Chat Completions 接口，配置项为 `OPENROUTER_API_KEY`、`OPENROUTER_MODEL`。密钥仅在服务端读取，不进入浏览器配置。
- 发起模型请求前验证 Supabase 用户和工作区权限；输入上下文只包含当前用户有权访问的数据。模型提案校验后通过 Supabase 数据库函数原子提交。
- 模型 ID 使用 OpenRouter 实际目录中的完整标识，不以“ChatGPT”作为 API 模型 ID。首轮三种任务共用一个指定模型，不做自动模型切换。
- 采用 `response_format.type = json_schema`、严格 schema；路由设置 `provider.require_parameters = true`。实施时核对具体模型和路由是否支持所需参数，不静默降级为不受约束的文本解析。
- 仍执行本规格规定的本地 schema、目标 ID、日期、版本校验。结构化格式不代表语义正确。
- 首版请求完整返回后再应用，不边生成边修改事项。超时、拒绝、截断和限流进入可恢复失败状态。
