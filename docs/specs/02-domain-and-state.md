# 02 · 数据与状态

本文件规定领域含义和一致性要求。用户已确定 Supabase 作为数据服务，持久化采用其 Postgres；SQL 和调用实现遵守下列规则，不再维护独立的本地数据库副本。

## 核心对象

| 对象 | 最小内容 | 约束 |
| --- | --- | --- |
| Workspace | ID、owner_user_id、时区、默认语言 | MVP 一个用户、一个工作区，所有权关联 Supabase Auth 用户。 |
| Page | ID、类型 daily/document、标题、日期（daily 专有）、版本、创建/修改/移除时间 | 同工作区每个日期仅一个 Daily Page。 |
| Block | ID、所在 Page、类型、顺序、内容或目标 ID、版本、移除时间 | ID 在编辑和排序后不变，首版不嵌套。 |
| Task | ID、标题、状态、计划日、准备关注日、截止、来源、暂停顺延标记、版本 | 任务独立存在，页面行引用该 ID。 |
| Event | ID、标题、发生日、可选起止时间、时间说明、时区、状态、来源、版本 | 一次单日事件；没有明确时间则不编时间。 |
| Capture | ID、原始输入、录入时间/时区、来源 Page/位置、处理状态、关联请求与产物 | 原话在 AI 失败或整理后仍可查看。 |
| Reference | 引用 Block 的目标 Page/Block | 可通过 Block 字段表达，不强制独立表。 |
| DailyPlacement | 日期、Task ID、呈现状态 suggested/included/excluded、来源 | 同任务同日只有一条有效安排关系；多处普通引用可存在。 |
| Review | ID、所属日期、原话、关联 Capture、草稿生成状态 | 原话与 AI 总结分开。 |
| Change | 操作 ID、目标、前后值、时间、操作者、来源 Capture | 覆盖事项状态/日期、移除、AI 应用及撤销，支持追溯与条件撤销。 |
| Generation | 请求 ID、目标日期/Page、输入版本、状态、输出或失败原因 | 重试不重复创建每日页或事项。 |

版本使用可比较的修订号即可，不要求全量事件溯源。普通逐字输入不要求保存永久逐键历史；事项变更和应用 AI 前的内容需保留恢复依据。

Capture 处理状态为 saved / processing / needs_clarification / applied / failed / superseded。编辑待处理原话时旧请求进入 superseded，新内容需重新处理；不得把旧结果当成新输入的成功结果。

Generation 状态为 pending / running / ready / applied / failed / superseded。ready 表示结果已准备，applied 才表示内容已保存到目标页；有人工编辑时可以停留在 ready 等待合入。

## Page 与 Block

Page 是正文容器。Daily Page 的日期是归属日，不随某个任务改期而改变。

基础类型：paragraph、heading、list_item、quote、task、event、reference。

- 文字类 Blocks 保存用户文字；quote 表示独立摘录，可附来源引用。
- task/event Blocks 绑定独立 Task/Event，可在多个页面出现。
- reference 指向 Page 或普通 Block；对任务/事件选取引用时，使用对应关联块，保持可操作状态。
- 页面引用预览只展开一层，不递归渲染全部引用链，互相引用不得导致循环加载。
- 来源 URL、资料原文、个人备注、AI 摘要在展示上可区分，不能把摘要当原文覆盖。

同一任务在同一每日页可以被用户再次引用，但每日安排列表/候选计数与 AI 草稿必须按 Task ID 去重。完成任何一处，其余关联行同步状态。

## 日期与时间

| 字段 | 意义 | 没有值时 |
| --- | --- | --- |
| captured_at | 实际录入时间，包含时区基准 | 不允许缺失。 |
| page.date | 日记归属日期 | 普通 Page 无此字段。 |
| task.planned_on | 用户明确安排处理的本地日期 | 未安排，不视为逾期。 |
| task.attention_on | 用户指定从哪天开始准备/关注 | 不猜提前天数。 |
| task.deadline | 截止的本地日期，可有明确时间，保存其时区 | 没有截止，不等于不重要。 |
| event.date/time | 事件发生日与明确时间 | 日期已知、时间模糊时保存原时间说明。 |

日级字段按 YYYY-MM-DD 表达，不能直接当 UTC 午夜再转换导致偏一天。明确时刻保存时区和实际时刻；换时区不重分配已有日记归属日。

相对日期基于 Capture 的录入时间和时区；不是模型请求完成时间、服务器日期或当前查看的历史页日期。用户在历史页输入“明天”时仍按录入当下解析，回执明确具体日期；若表达“这一天的明天”则参照明确日记日期。

试验默认：周一作为周的起点，“下周五”指录入当周的下一周周五。“周五”“这周”等出现过去/未来歧义时回执展示解释，存在两个合理对象或日期且影响安排时提问。日期缺少必要信息时保留未安排，不伪造精确提醒。

任务的处理日、准备日、截止可以不同，不得以改计划日为由自动改截止。用户明确表示“截止也顺延”才能改两个字段。

## Task 生命周期

```text
open ──完成──> done
open ──取消──> cancelled
done / cancelled ──明确恢复──> open
```

暂放、等待、逾期不是完成状态。首版“等待回复”保留为 open，可暂停自动顺延并存等待说明；不增加自动依赖链。

任务在何处出现与任务是否存在分开：

- `suggested`：建议今天做，尚未改变用户原计划日。
- `included`：用户明确选择或日期安排进入当日计划。
- `excluded`：该日被明确移出，重复生成时不得重新加入正文。

“建议接续”引用已有任务，不新建 Task。AI 提出的新行动先是普通建议文字，用户转为待办后才创建 Task。

## 一步暂放的状态变化

对于今天的 Task：

1. 当日 DailyPlacement 设为 excluded，移出当日正文安排。
2. `auto_carry_paused = true`，阻止仅因未完成而自动接续。
3. 如果 planned_on 就是该日，清除该计划日；已有明确未来计划日保留。
4. Task 保持 open，deadline 与 attention_on 保留。
5. 保留 Change，支持无冲突撤销。

用户后续明确指定新计划日、点击“今天做”或主动恢复自动接续时，更新 planned_on 和对应 placement，清除暂停标记。截止和明确关注日不会因为暂停而失效。

移除未来日期页的任务安排：同样仅取消该日安排，若 planned_on 与该日期相同则清除，暂停未完成自动顺延；保留截止。操作明确反馈影响日期。

移除历史页任务引用：只删除该引用，不改今天的 placement、Task 日期或暂停标记。

移除普通资料引用：只移除 Reference Block，不触发以上任务状态规则。

## 每日构建与回流

### 事实集合

日期 D 的事实由已保存的数据确定：

- Event 发生日等于 D。
- open Task 的 planned_on 等于 D。
- open Task 的 attention_on ≤ D，且尚未完成/取消；进入关注区域，可按需展开。
- open Task 的 deadline 在 D 到期或已过期；保留到处理或明确改期。

attention_on 已到但正文被暂放的任务仍可在关注区域找到；它不是“再次推荐今天做”，应显示“准备时间已到，已暂放今日安排”。同日操作后不得立刻重新插回正文。

未来页的明确日期安排可以提前查看；“已到期”等措辞只在真实本地今天判断。查看明日页时显示“当日截止”，不声称事情现在已逾期。

### 接续候选

从 D 之前最近一份有效每日计划中，寻找仍 open、未 excluded、未暂停自动接续，且没有另一个明确未来计划日的任务。以原有顺序取最多 3 条作为默认候选，不让模型凭空选择整个库存。

候选、事实、已有正文按 Task/Event ID 去重；超出候选上限的内容可在 review 中展开，截止事实不受上限影响。

### 页面生成

- 查找或创建 date=D 的唯一 Page；生成不等于创建任务。
- 已有人工内容或已应用草稿时，后续生成只能提出更新，不重建整页。
- 同一任务在候选、事实和用户正文出现时保持单一安排关系。
- 新到日期事实先更新日期状态区；用户可合入正文，不悄悄替用户排序。
- AI 输出基于旧版本时保留为待应用结果，重新核对或再生成，不覆盖新编辑。

## Event 规则

Event 状态为 active/cancelled，过去的 active 事件成为历史，不自动顺延、不自动改为 done。

准备或跟进工作用独立 Task，可关联 Event。修改事件日期不隐式改变所有相关任务；用户明确要求“准备工作也顺延”时，给出具体变更回执后更新明确关联的任务。缺少关联或有多个候选时先澄清。

## 引用、移除与恢复

- 所有引用使用稳定 ID，不依赖标题唯一或正文字符串匹配。
- 标题改名、Block 移动不改变引用目标。
- 普通 Block 或 Page 被移除时先保留软删除记录；引用显示目标已移除，可恢复，不能错误指向另一段内容。
- 删除资料 Page 不级联取消其中显示的独立任务/事件。
- Daily Page 被移除后该日期唯一性仍保留；再次打开提供恢复入口，不创建同日第二份页面。
- 任务/事件取消与资料移除采用不同操作。试用期不做自动永久清理。
- 反向引用由实际引用关系计算；删除引用后相应反向引用消失。

## 写入与失败一致性

- Capture 先可靠保存，之后才能请求 AI。
- 同一次已校验 AI 操作集合原子写入，失败则不出现半个任务/半个引用；原 Capture 保留。
- 在 Supabase Postgres 中用一个受控数据库函数/RPC 提交关联写入，在同一事务内检查版本、更新对象、维护引用和记录 Change；不能把多个独立 HTTP 写请求当成原子事务。
- 模型请求在事务之外执行，不能在等待 OpenRouter 时占用一个数据库事务。
- 每个提交/应用有幂等操作 ID。刷新、重试和双击不会复制同一产物。
- 对已存在对象的更新校验版本。冲突时保留双方内容，不静默覆盖。
- 撤销使用对应前后值且校验当前版本；不能把后续完成或编辑一起回滚。
- 保存失败的本地输入在当前会话中保留；界面必须区分“本地待保存”和“已持久保存”。不得在失败时承诺刷新后仍可恢复。

## Supabase 所有权和访问

- 每条工作区数据包含 workspace_id；Workspace 保存 owner_user_id，首版只允许所有者访问。子对象关联必须属于同一工作区。
- 启用相应 RLS 规则，未登录不能访问个人页面、来源、Capture 或事项。通过新增一个工作区并不开放其他用户的内容。
- 服务端验证会话，再使用带用户身份的 Supabase 客户端调用数据操作；正常读写不依赖绕过 RLS 的管理员凭证。
- 数据库函数默认采用调用者权限，并限制执行范围；如确需提升权限，单独明确所有权校验和调用授权，不能信任客户端或模型给出的 user_id。
- 模式、索引、约束、RLS 与函数以版本化 SQL 迁移保存；应用和迁移均指向所选 Supabase 项目，不在真实试用时偷偷回退到浏览器存储。

## 导出

首版提供可还原关系的结构化 JSON 导出，包含 Pages、Blocks、Tasks、Events、来源、引用、Capture、Review 与必要变更记录。ID、日期类型、时区和引用关系必须保留。

同时可提供易读 Markdown 导出；若为降低成本只先完成一种，JSON 是验收必需，Markdown 属于后续便利功能。没有实现导入时，不把导出描述为已验证的完整备份恢复。
